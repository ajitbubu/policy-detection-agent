WHAT CHANGED (plain English)
---------------------------------------------------------------
The CNIL adopted a final amendment to its existing cookie recommendation on 18 December
2025 (published in the French Official Journal on 18 January 2026 as deliberation
2025-131) establishing a framework for collecting a single cookie/tracker consent that
is automatically honoured across all authenticated devices linked to the same user
account (computer, smartphone, tablet, connected TV, etc.). Prior to this recommendation,
there was no CNIL guidance on cross-device consent propagation; each device was treated
independently, requiring re-consent on each new device even for logged-in users.

The new framework is OPTIONAL -- organisations are not required to implement multi-device
consent. However, if an organisation does implement it, the CNIL mandates that:
(a) prior consent collected without disclosing the multi-device scope cannot be reused --
    consent must be re-solicited with that scope explicitly disclosed;
(b) consent must be centralised at the account level, not at the device level;
(c) data controllers must NOT share raw authenticated user identifiers with subcontractors,
    including CMPs -- the CNIL specifically calls out CMPs and requires use of
    pseudonymized technical identifiers when interfacing with consent management
    tooling; and
(d) the consent record must accurately reflect the multi-device scope of consent given.

The CNIL also announced that follow-on 2026 work will address cross-domain consent
(single consent valid across multiple sites or media belonging to the same group),
which is relevant but not yet published as formal guidance.

---------------------------------------------------------------
WHO IS AFFECTED
---------------------------------------------------------------
Applicability test:    Any organisation subject to French data protection law (and by
                       extension, organisations in other EU/EEA states serving French
                       users) that operates authenticated user accounts and uses cookies
                       or similar trackers. Specifically relevant to organisations that
                       want to offer seamless cross-device consent experiences.
DataSafeguard customers likely affected: Customers with authenticated user flows
                       (e.g., media groups, e-commerce, SaaS platforms) who want to
                       propagate consent choices from one device to another without
                       re-prompting. Estimate: high-value enterprise accounts with
                       multi-device user bases.
Customer notice required:  YES -- advisory to customers explaining the pseudonymization
                       requirement when passing authenticated identifiers to ID-PRIVACY
                       as a CMP. This requirement applies NOW to any customer already
                       attempting cross-device consent via the platform.

---------------------------------------------------------------
ID-PRIVACY IMPACT
---------------------------------------------------------------
Affected subsystems:
  [X] Consent Banner               -- If a customer enables multi-device consent, the
                                      consent prompt on first device must explicitly
                                      disclose that "your consent choices will apply
                                      across all your logged-in devices." Existing
                                      consent records that lack this disclosure cannot
                                      be reused for multi-device propagation.
  [ ] Cookie Classification ML     -- No classifier change required.
  [X] Consent Storage & Proof      -- Consent records for multi-device scenarios must
                                      carry a multi_device_scope flag and must be
                                      stored at the account level (linked to a
                                      pseudonymized account identifier, not a raw user
                                      ID or device ID). New schema field: account_level
                                      (bool), multi_device_scope_disclosed (bool),
                                      pseudonymized_account_id.
  [ ] Consent Signals (GPC/TCF/GPP) -- No direct change to signal format, but the
                                       consent record that backs a TC String or GPP
                                       string must now optionally reflect account-level
                                       scope.
  [X] Geo / Jurisdiction Routing   -- FR jurisdiction config must expose a "multi-device
                                      consent enabled" toggle. When enabled, the platform
                                      activates account-level storage and pseudonymized
                                      identifier flow.
  [X] Vendor / SDK Governance      -- CRITICAL CMP-specific requirement: ID-PRIVACY must
                                      NOT receive or process raw authenticated user
                                      identifiers from the customer's auth system. The
                                      integration must use a pseudonymized technical ID
                                      (e.g., an HMAC of the user ID with a customer-
                                      controlled key). This requires a documented
                                      integration pattern and potentially a new SDK
                                      parameter for customers passing account context.
  [ ] DSR Engine                   -- No immediate change, but account-level consent
                                      deletion should propagate across all devices on a
                                      DSR erasure request (verify existing behaviour).
  [X] Audit / Logging              -- Multi-device consent records must log: devices on
                                      which consent was collected, the pseudonymized
                                      account ID, whether the multi-device scope was
                                      disclosed at collection time.
  [ ] Cross-border transfer        -- Not directly affected.
  [X] Tenant Config / Admin UI     -- New optional feature flag per tenant: "Multi-device
                                      consent (FR -- CNIL 2025-131)". When enabled,
                                      expose: pseudonymized account ID input, multi-device
                                      disclosure text field, account-level storage toggle.
  [X] Documentation / DPIA / RoPA  -- New integration guide: "How to configure ID-PRIVACY
                                      for CNIL-compliant multi-device consent." Must
                                      specifically address the pseudonymized identifier
                                      requirement and warn against passing raw user IDs.

     `account_id_token` (HMAC or opaque token generated by the customer's backend).
     ID-PRIVACY must never receive the raw user ID. Validate that the token format
     cannot be reverse-engineered. -- est. 8 pts -- by 2026-07-11
  2. Implement account-level consent storage: allow consent records to be keyed on
     pseudonymized_account_id (in addition to the existing device/cookie-jar key).
     When account-level storage is active, a consent choice on device A is surfaced
     on device B when the same account token is presented.
     -- est. 13 pts -- by 2026-07-25
  3. Add multi_device_scope_disclosed flag to the consent record schema; reject
     propagation of any consent record where this flag is false (preventing re-use
     of old consent records for multi-device scope).

DEPENDENCIES / BLOCKERS:

    format; legal judgement required on what constitutes a compliant pseudonymization.
  - Cross-domain consent guidance (follow-on from this recommendation) is pending;
    watch CNIL publications in H2 2026.
  - Feature is optional; customer adoption will depend on their own authenticated
    account architecture.

---------------------------------------------------------------
RISK IF NOT ACTIONED
---------------------------------------------------------------
The feature is optional -- customers are not required to implement multi-device consent.
However, if a customer already attempts to pass authenticated identifiers to ID-PRIVACY
for cross-device correlation, they are already non-compliant with the CNIL requirement
that CMPs not receive raw user identifiers. This creates direct CNIL enforcement exposure
for the customer and potential data-processor liability for DataSafeguard. The maximum
CNIL fine is EUR 20M or 4% global turnover. The primary action needed is the customer
advisory and the pseudonymized identifier architecture, even if the full multi-device
feature ships later.
