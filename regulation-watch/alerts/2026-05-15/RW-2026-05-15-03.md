WHAT CHANGED (plain English)
---------------------------------------------------------------
By Provision No. 284 of 17 April 2026, the Italian Garante issued binding
guidelines on the use of tracking pixels in email communications, published in
the Official Gazette on 29 April 2026. Prior to this, the Garante had not
issued specific guidance on email tracking pixels, which were processed under
the general cookie/tracker framework. The provision classifies email tracking
pixels as a form of access to terminal equipment subject to the same consent
rules as cookies (Article 122 of the Italian Personal Data Protection Code /
Article 5(3) ePrivacy Directive). Three specific requirements distinguish this
from the French CNIL recommendation: (1) consent must be granular and
specifically separate from marketing consent; (2) withdrawal rights must be
granular -- the user must be offered three options: continue receiving emails
WITH tracking, continue receiving emails WITHOUT tracking, or stop all
communications; (3) any entity sending emails with tracking pixels must conduct
an impact assessment for each purpose category. The Garante explicitly states
that deliverability measurement for inactive suppression is exempt, but all
other purposes require prior informed consent. The provision applies to all
senders: companies, public administrations, ESPs, and marketing automation
platforms. The six-month grace window expires 28 October 2026.

ID-PRIVACY PLATFORM IMPACT
---------------------------------------------------------------
Affected subsystems:

  [X] Consent Banner / Consent Capture & Storage
      The Garante's three-tier withdrawal model ("tracking on / tracking off /
      all emails off") is more granular than any current ID-PRIVACY email
      consent flow. The consent capture schema must be extended to support
      three discrete consent states for email tracking for Italian subscribers.
      This is a data model change: a boolean "email pixel consent" is
      insufficient; the schema needs an enum: {tracking_with_email,
      email_only_no_tracking, no_email}.

  [X] Cookie Classification ML
      Same extension as noted in RW-2026-05-15-02: "email_tracking_pixel_IT"
      label with Italian-specific consent requirement and a deliverability
      exemption label. Italy's requirements are more stringent than France's
      on the withdrawal granularity dimension; the classifier must surface this
      difference.

  [X] Consent Signals (GPC/TCF/GPP)
      Not directly affected for standard web signals, but if ID-PRIVACY
      implements a unified consent signal layer across web + email, the Italian
      email consent state (three-tier enum) must be expressible in that signal
      layer.

  [X] Geo / Jurisdiction Routing
      Italian jurisdiction ruleset for email pixel tracking must be added.
      Italy's ruleset is distinct from France's (three-tier withdrawal vs.
      binary opt-out). The routing logic must fire the Italian ruleset when
      jurisdiction_code == "IT" for email tracking purposes.

  [X] Vendor / SDK Governance
      ESPs operating in Italy must be flagged for the three-tier withdrawal
      requirement. If the ESP's API does not support suppression at the
      "email without tracking" level (i.e., the ESP can only do "send" or
      "unsubscribe", not "send without pixel"), the vendor must be flagged as
      INCOMPATIBLE for Italian deployments. This is a vendor capability gap
      check that should be added to the vendor assessment questionnaire.

  [X] Audit / Logging
      The Garante's provision requires a documented impact assessment per
      purpose category. If ID-PRIVACY generates or assists with DPIA outputs,
      the email tracking pixel purpose must be added as a processing activity
      in the RoPA / DPIA template for Italian customers.

  [X] Documentation / DPIA / RoPA
      Update Italy jurisdiction fact sheet. Add email tracking pixel as a
      processing activity in the default Italian RoPA template. Flag the
      three-tier withdrawal requirement as a vendor capability prerequisite.

  [ ] DSR Engine           (existing access/delete rights sufficient)
  [ ] Cross-border transfer (not directly changed)
